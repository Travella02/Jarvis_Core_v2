# 0.1.2 Repair6-Repair9 — Follow-up completion safety, not a latency solution

Observed Windows live test on Repair8: direct voice playback at 7,932 / 3,628 / 3,319 ms versus ~498 ms gate-free Mini baseline; correct tool selection for `ask_luna` and `test_action` but both subsequent spoken dry-run replies ended incomplete at precisely 384 tokens and were suppressed. Barge-in canceled playback correctly.

Changes: expand the dry-run tool follow-up budget to 1024 combined text/audio tokens, force one short truthful sentence; handle WebRTC drain event before/after `response.done`, preserving fail-closed playback with idempotent finalization; publish a verified *text-only failure* and return to idle if a follow-up nevertheless fails. Never play partial audio or execute Luna/actions in this experimental mode.

**Architectural conclusion**: entire-response capture delays first speech until the answer ends. It cannot recover the ~500 ms direct-speech baseline. Keep the mode as a diagnostic experiment only; the next architecture should measure an early authorization/parallel-isolated audio design with a hard permission and speech publication boundary. Do not ship whole-answer buffering as normal Jarvis behavior.

V1 comparison: event ownership and deterministic tool authority remain separate. None of V1's completed audio cancellation patterns authorizes playback of unverified speech; this repair preserves that boundary and addresses only observed follow-up failure.

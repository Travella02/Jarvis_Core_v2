# 0.1.2-repair6-repair14 — Reuse healthy local Whisper listener

Observed on Windows: wake startup loops with `ConnectionResetError [WinError 10054]` while a standalone diagnostic reports port 18080 already listening and a successful Whisper warmup. Provider `_ensure_server()` unconditionally spawned a new `whisper-server` when a healthy server was already listening, then treated the old server's root response as readiness for the newly launched process. That could conflict on the same port and disrupt wake readiness.

Repair: reuse an existing responsive localhost Whisper service; repeat probe under the provider start lock; do not spawn another child while this provider has one starting. `close()` still only stops the child this provider launched, not a pre-existing server. Existing wake phrase policy, audio, Realtime Mini, and dry-run tools unchanged.

Automated checks cover a ready pre-existing server, normal cold startup, a managed server becoming ready, and hidden warmup without duplicate subprocess creation. Need live Windows acceptance: wake from sleep by saying "Jarvis" and embedded full wake command; confirm `[Jarvis Wake] phase=ready`, `phase=listening`, and detection, without repeated WinError 10054.

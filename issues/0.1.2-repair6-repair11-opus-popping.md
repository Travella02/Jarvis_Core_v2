# Repair6–Repair11: Opus re-encoding / stream pops

## Live failure (Repair10)
Parallel text-only tool decision was correct; direct first-audio playback was approximately 472–680 ms, and tool-selected turns were not audible. However, the user heard recurring popping throughout Cedar responses. Repair10 captures remote WebRTC audio with 100ms `MediaRecorder` Opus chunks and appends their WebM bytes to a `MediaSource` in sequence mode. Audio glitches at boundaries, buffering, or MSE/WebM timestamp irregularities are plausible. This diagnosis is not verified without audio recordings.

## Scoped repair hypothesis
Do not repeat text-to-speech sentence slicing or whole-recording playback. Replace the private audio transport **only in `mini-overlap`** with an `AudioWorklet` PCM ring buffer. WebRTC audio frames flow into a worklet, which emits zeros until the independent tool-decision response authorizes direct speech; after authorization, it outputs ordered, original PCM samples from one continuous generation. No MediaRecorder Opus encoding, WebM container, SourceBuffer, or per-chunk append/decoder restarts. Use a small startup jitter buffer and short ramps to avoid transients. Silent tool-selected turns discard the PCM gate; all actions remain dry-run.

The provider HTML audio element remains muted. Default routed and `mini-fast` modes are unchanged. Interrupt cancels the worklet and closes its AudioContext. The 8-second preauthorization cap and resource/session failure paths fail closed. Measure first audible PCM, glitches, missing syllables, and CPU utilization on Windows before accepting.

## V1 comparison
V1 reference `Jarvis_0.3.6_clean_checkpoint.zip` uses cloud Realtime streaming directly; it does not repeatedly synthesize sentence-sized voices or rewrap 100ms Opus segments for user playback. Keep continuous streaming, tool authority, and turn-scoped cancellation while changing only private playback implementation.

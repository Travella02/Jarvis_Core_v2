# 0.1.2-repair6-repair12 — Out-of-band response input isolation (experimental)

## Live failure
Repair11's PCM playback removed audible popping but the turn-2 *generated text* repeated part of turn 1's Mars answer. A real-world background-build request was classified `direct`, and a separate casual turn requested Luna unexpectedly. This is **not accepted**.

## Root-cause hypothesis and deterministic protection
The overlap prototype dispatched two `conversation:'none'` responses on VAD `speech_stopped`, before confirming the new input audio item had been committed to conversation. An out-of-band response does not write output into the default conversation, but without `input` it still uses the implicit current context. This permits older context or an unfinished item boundary to affect the request.

Now both independent responses wait for `input_audio_buffer.committed` and supply identical explicit `input:[{type:'item_reference',id:item_id}]`. Text-typed turns get an explicit text input. Missing input fails closed after two seconds. Response-created/done ownership verifies the response metadata `jarvis_turn`. Old turn cancellation clears the pending audio item, timer and current owner.

## Boundaries and known limitations
No semantic intent heuristic; no word-based shortcuts. Separate responses are still speculative, tool actions remain dry-run, and the audio isolation path remains PCM. Explicit-current-turn input intentionally lacks the previous conversational turns. Multi-turn context must later be rebuilt using **selected authoritative** earlier items only; never speculative responses. This change can add input-commit waiting latency and needs Windows/Electron validation. The root-cause hypothesis cannot be proved from previous screenshots alone.
